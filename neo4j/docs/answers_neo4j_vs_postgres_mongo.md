# Ответы на вопросы п.8 (Работа с данными)

## Какие задачи лучше решаются в Neo4j, нежели в Postgres/Mongo?

1. **Обход связей произвольной глубины** — «кто связан с кем через N шагов», «все соседи до 4 звена». В SQL нужны рекурсивные CTE или множество JOIN; в Mongo — сложные агрегации. В Cypher: `MATCH (a)-[:REL*2..4]-(b)`.

2. **Поиск общих соседей и рекомендации** — «клиенты, бравшие те же книги», «книги одного автора», «кто с кем связан через общие узлы». В графе это один-два MATCH по рёбрам; в реляционной модели — несколько JOIN по разным таблицам.

3. **Запросы вида «путь между двумя сущностями»** — кратчайший путь, все пути, пути с ограничениями по длине/типу. В Neo4j заложена модель графа и индексы для обхода; в PG/Mongo такие запросы громоздкие.

4. **Модели с множеством типов связей и ролей** — «клиент брал копию», «копия в офисе», «книга написана автором», «клиент рекомендует книгу». В графе каждая связь — ребро с типом и свойствами; в SQL — много таблиц связей и JOIN’ов.

5. **Агрегации по «соседям»** — «топ авторов по числу взятых книг», «офисы по количеству выдач». В Cypher это обход по рёбрам + `count`/`collect`; в PG — несколько JOIN и GROUP BY.

---

## Какие — хуже?

1. **Строго табличные отчёты** — плоские выборки с десятками колонок, без навигации по связям. Реляционная БД и SQL к этому лучше приспособлены.

2. **Тяжёлые аналитические агрегации** — большие объединения таблиц, окна (RANK, PARTITION BY), сложная аналитика. В Neo4j меньше оптимизаций под такие сценарии, чем в PostgreSQL.

3. **Транзакции с массовыми обновлениями** — обновить одно свойство у миллионов узлов по условию. В PG/Mongo пакетные UPDATE/aggregation pipeline привычнее и часто быстрее.

4. **Жёсткая схема и ограничения целостности** — много типов ограничений (FK, CHECK, триггеры). В Neo4j есть уникальность и существование свойств; сложные бизнес-правила проще обеспечивать в реляционной БД.

5. **Хранение больших документов/бинарных данных** — Neo4j ориентирован на граф; для «документа» с вложенными структурами MongoDB или PG с JSON часто удобнее.

## Где в нашем проекте (Library) логично и оправдано использовать Neo4j?

1. **Рекомендации и «похожие читатели»** — клиенты, которые брали те же книги или рекомендуют те же книги; книги одного автора/жанра. Это типичные графовые запросы (общие соседи, пути по графу интересов).

2. **Аналитика по цепочкам** — «какие офисы связаны общими книгами», «клиенты, связанные через общие выдачи», «авторы, чьи книги чаще берут в одном офисе». В Cypher это короткие запросы; в PG — много JOIN и подзапросов.

3. **Поиск пути «клиент → книга → автор → другие книги»** — предложить «кто брал это — брал ещё то». Хранение и обход таких связей в графе естественны.

4. **Не заменять полностью Postgres/Mongo** — основные данные (клиенты, выдачи, резервации, каталог) можно оставить в PG/Mongo; Neo4j использовать как слой для графа «кто что брал / что кому рекомендовано» с синхронизацией из основной БД (ETL или события). Так мы получаем сильные стороны каждой СУБД.
